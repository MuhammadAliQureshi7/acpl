# Taste
- When extending an existing application (e.g., adding new reports/screens), prefers the new work to follow the current established report format and layout already present in the codebase, rather than introducing a new format. Confidence: 0.6
- When a bug can be resolved either by fixing the data/file or by patching application code, prefers the non-invasive data/file-level fix (chose "flatten the import file with valid values, no app code changes" over patching the importer). Confidence: 0.5
- When reporting a problem (e.g., a failed import), explicitly wants the underlying root cause explained ("let me know what is causing these errors") rather than just being handed a fix. Confidence: 0.5
- When asking for data to be listed (e.g., account types used in a file), wants the answer formatted as PHP arrays mirroring the exact structure in the source model (with `id`, `_l('lang_key')`, `order` fields) rather than plain descriptive prose. Confidence: 0.6
- When asking to inspect/extract data from files (e.g., which accounts have a hyphen, listing type names), prefers the answer shown directly in the chat response rather than any file being created or edited ("just give it here instead of editing any file", "just give me name of types..."). Confidence: 0.8
- When showing PHP data arrays (e.g., account type lists), wants each element written as its own expanded multi-line array block with one key per line (`'id' =>`, `'name' =>`, `'order' =>`), formatted exactly like the module's existing arrays — not compact one-line-per-element entries ("they should have their own array instead all inside one array... just like them"). Confidence: 0.7
- When troubleshooting why figures/amounts don't show in the app, directs the investigation to the live database (actual stored rows, settings, references) rather than concluding from code or spreadsheet analysis alone — ground-truth checks against real data are expected ("check database and let me know are they mapped accurately"). Confidence: 0.6
- When the end client must supply and maintain their own data file (e.g., their own chart of accounts), prefers making the application accept that file as-is — translating its vocabulary to native/internal structures inside the code — over reformatting the file or sending a fixed template back to the client (the client rejected the developer's "fixed" file because they want to keep/add their own accounts). This refines the earlier data-file-fix preference: it applies only where the user controls the data, not when an external client owns it. Confidence: 0.7
- Import/translation solutions must stay open for records the client adds later on their own (generic fallback defaults for unknown codes/subtypes), not just a static map covering the current file's rows ("they want to add their own accounts"). Confidence: 0.6
- After a previously proposed approach is rejected (e.g., by the client), expects the agent to directly implement the adjusted solution rather than re-presenting options and asking which to proceed with ("I just want you to give me a solution according to that file"). Confidence: 0.5
- After a data migration fix (e.g., remapping deleted chart-of-accounts ids), expects the agent to sweep and fix ALL remaining related mappings/settings in the same pass — not just the ones tied to the reported symptom — and to report that zero dead references remain ("check for other mapping as well"). The user continued to follow up on remaining flows in later turns ("purchase invoice and its payments has to be mapped and also sales and purchase invoices taxes", then "Ok now I need one for tax receivable and payable"), confirming mapping must be functionally complete across every posting flow, not just structurally valid. Confidence: 0.9
- "Mapped/posted" is judged by the end state on the books, not by configuration: when records fall outside the module's automatic conversion flow (e.g., standalone purchase invoices with no linked purchase order), the user still reports them as a problem ("purchase invoices are still not mapped") rather than accepting an explanation that the module can't convert them. The accepted resolution was to post those legacy records directly to the ledger as double-entry rows (DR Cost of Goods Sold / CR Accounts Payable) with dedupe checks and balance verification — a data-level fix, not an app-code change — leaving nothing unposted that should appear on the books. Confidence: 0.6
- After an explanation of how a flow/config behaves (e.g., tax receivable/payable mapping), asks probing follow-ups to verify it against the real system — both the data source ("from where is it getting the tax") and the code triggers/timing ("can you check when it is storing invoice data into tblacc_account_history") — and expects the answer traced end-to-end through the actual stored data (tax definitions, per-line taxes, mapping tables) and code (hooks, conversion conditions, status-change handlers), not asserted from configuration alone. The user also cross-checks posted ledger balances against sums over source columns (e.g., GST Payable 71,000 vs. invoice total_tax sum 96,000) and expects the mismatch reconciled record-by-record with a clear statement of which source is authoritative (continued this pattern by questioning Sales Revenue 12,570,000 against invoice totals 12,641,000 and hypothesizing the posting derives from subtotal rather than total). Confidence: 0.8
- When a module's built-in flow doesn't match their actual business process (their purchase documents are purchase invoices, not purchase orders), expects the module to be changed to fit the business ("instead of purchase order it has to take purchase invoice") — wiring automatic conversion on invoices across all layers (model conversion, badge counts, transaction list, one-click/bulk convert, payments) rather than being steered toward the module's default workflow (e.g., creating purchase orders) or one-off manual backfills. Code-level module changes are acceptable when the goal is making automation match the real document flow. The user follows up on each remaining surface (mapping setup included) until the whole module — labels and behavior alike — treats purchase invoices as the purchase document. Confidence: 0.8
- When the terminology shown in a module no longer matches the document type actually used (e.g., the mapping setup and transaction screens still say "Purchase Order" but the business deals in purchase invoices), expects every visible label — config section headers, tab titles, table column headers, and language strings — to be renamed consistently to the real document name, across the whole module, not only in the conversion code path. Confidence: 0.6
- When a mapping target is clear for one side of a mirrored flow but not the other (e.g., sale invoice tax must land in "Sales Tax / GST Payable", then "for purchase invoice find something similar and suggest me"), wants the agent to first verify where that value actually flows in the code/DB and then propose the analogous counterpart account for the opposite side (sales tax as payable/liability vs. purchase tax as the recoverable input-GST side), presented as one concrete, data-checked recommendation rather than a menu of options or an open question back. Confidence: 0.5
- Treats the tax field carried on an invoice (sales `total_tax` / total − subtotal) as real tax that must be posted to the designated tax account ("total_tax is tax and should be mapped with Sales Tax/GST Payable") — when a module's conversion only posts per-line tax and the tax sits inside the invoice total, expects the conversion logic to be patched to post the residual (total − line amounts) to the tax account so AR equals invoice totals and GST is fully captured, and previously-converted invoices to be reconverted the same way. Confidence: 0.6
